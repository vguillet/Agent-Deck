# Client protocol v2

REST is rooted at `/api/v1`. Collection responses contain `items`, an optional
opaque `nextCursor`, and `asOfSequence`. Clients should fetch a snapshot, open
`/api/v1/stream`, register, and subscribe after the snapshot watermark.

```json
{
  "type": "register",
  "client": {
    "id": "stream-deck:device-id",
    "type": "stream-deck",
    "name": "Office XL",
    "version": "0.1.0",
    "capabilities": {
      "notifications": true,
      "images": true,
      "animations": true,
      "textInput": false,
      "approvalActions": false
    }
  }
}
```

After `registered`, send:

```json
{
  "type": "subscribe",
  "topics": ["agents.summary", "attention", "providers.health"],
  "afterSequence": 1842,
  "filter": {
    "providers": ["codex", "cursor-cloud"],
    "states": ["running", "waiting_for_approval", "ready_for_review"]
  }
}
```

Events are delivered as `{ "type": "event", "event": { ... } }`. A
`stream.resync_required` response means the requested sequence predates the
bounded transport replay buffer and the client must fetch a new REST snapshot.

Running agents may include privacy-safe progress:

```json
{
  "progress": {
    "activity": "planning",
    "plan": { "completed": 2, "total": 5 },
    "observedAt": "2026-07-29T09:42:31.000Z"
  }
}
```

`activity` is an allowlisted coarse category. `plan` is present only when a
recognized plan/Todo tool reports structured statuses. Providers discard step
text, raw tool names, tool arguments, and results before emitting progress.
Changes are delivered as `agent.progress.changed` events on `agents.summary`.
Because Cursor does not emit its native todo updates through tool hooks, the
local `sessionStart` hook injects an instruction to run
`true # agent-deck:progress <completed> <total>` immediately before each todo
update. The sanitizer retains only the two bounded integers.

The server disconnects clients with close code `1013` when their output buffer
exceeds 1 MiB. Clients should reconnect with exponential backoff and the last
processed sequence.

Client configuration is an opaque revisioned document. Updates may send
`If-Match: "<revision>"`; stale revisions receive HTTP 409.

Agents may include navigation links:

```json
{
  "rel": "focus",
  "label": "Open in Cursor",
  "href": "cursor://agent-deck.focus/open?conversationId=..."
}
```

`focus` requests application switching and `view` opens a non-primary
inspection surface. Opening them does not create a command or canonical event.
Local Cursor and Codex agents should use the brokered endpoint:

```http
POST /api/v1/agents/<agent-id>/focus
```

The response uses `opened`, `unavailable`, `ambiguous`, `timeout`,
`superseded`, and `failed`. `superseded` is a non-error result indicating a
newer machine-wide focus intent won. Cursor-window registrations may advertise
`focusKinds: ["cursor.conversation", "codex.thread"]`; focus intents then carry
a discriminated `target`. Registrations without `focusKinds` remain compatible
with legacy Cursor conversations. Sending a Codex target to such a window
returns an upgrade-required `unavailable` result.

Focus companion protocol v2 registrations additionally advertise
`focusProtocolVersion: 2` and accept
`{"type":"focus.cancel","requestId":"..."}`. The core activates the exact
window, waits for its focused-state report, then dispatches the intent. Focus
execution is serialized across brokered and direct Cursor links; obsolete
queued requests are discarded and late stale opens cause the newest target to
be reasserted.

Cursor conversations require exact normalized workspace-root equality. Codex
threads use `cwd` containment, prefer the longest matching workspace root, and
reject tied or duplicate windows. There is no standalone Codex fallback.

To cancel an active agent run, send:

```http
POST /api/v1/agents/<agent-id>/commands
Content-Type: application/json

{"action":"cancel","expectedRevision":7}
```

The response is a command result with a `succeeded`, `failed`, or `unsupported`
status. `expectedRevision` is optional; when supplied, a stale revision
receives HTTP 409. Successful providers emit the resulting canonical state
change.

To dismiss the currently visible activity epoch, send:

```http
POST /api/v1/agents/<agent-id>/dismiss
```

Dismissal stores the agent ID and `activityEpoch`, so repeated snapshots for the
same run or generation cannot recreate it, including after restart. A new
provider activity epoch restores the agent.

To dismiss every currently terminal agent, send:

```http
POST /api/v1/agents/dismiss-terminal
```

The response contains `{ "dismissed": <count> }`. Active agents are unaffected.
Agents and runs that leave the live projection generate `agent.removed` and
`run.removed`; there is no historical agent-event endpoint.
